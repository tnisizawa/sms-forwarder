# SMS転送のログ保持と復旧

## SMS転送メニュー（開発版HEAD）

スプレッドシートを開くと、SMS転送に次の3項目が表示されます。表示だけでは初期化・送信しません。操作時はGmailと現在のシートの既存権限に加え、ダイアログ用script.container.uiの承認が必要です。公開v16はこの変更をまだ含みません。

- 初期設定: settings・log・filterを補完します。GASエディタのsetupも同じ処理です。既存値・ルール・ログを削除せず、2回目も値を保持します。ヘッダー不一致では自動修復せず停止します。シート仕様は[SHEETS_SPEC.md](SHEETS_SPEC.md)。
- スマホの設定手順をメールで送る: ウェブアプリをデプロイし、公開画面に表示されたURL（/execで終わる）をsettingsの「ウェブアプリURL」へ貼り付けてから実行すると、自分宛へ手順メールを送ります。転送先アドレスを別に設定していても手順メールは自分宛です。URLは形式だけを確認し、公開状態・到達可能性・スクリプトとの対応は保証しません（正しい公開URLの貼り付けは利用者の責任）。未入力や不正形式では送らず、貼り付けを案内します。サービスからURLを自動取得する旧方式は廃止しました。
- テスト送信: 現在のfilterで判定したテストSMSを、現在の転送先へ送ります。不通過ではメールを送らず、その旨を表示します。結果はlogへ記録し、通常の保持上限を適用します。

合言葉を再生成する場合はsettingsの値を明示的に消し、初期設定を実行します。その後は端末側の合言葉も更新し、新しい手順メールを使って再設定してください。ログや他の設定は保持します。

開発版HEADへのpushだけでは公開ウェブアプリのバージョンは変わりません。公開判断と既存URLの扱いは塊6で行います。[RELEASE_BACKLOG.md](RELEASE_BACKLOG.md)へ未公開変更を残しています。

### 塊4Bの受入（2026-09-16 → 2026-09-17 に解消）

新規専用ブックは@HEADのみでもgetUrlがexec形式を返し、Service.isEnabledも送信を阻止しませんでした。修正前後に自分宛の手順メールが計2件送られています。このメールのURLは端末設定に使わないでください。初期設定2回の値保持、3シートのヘッダー、保護2件、ヘッダー固定、自分宛テスト送信1件とログの先頭ゼロ保持は実機確認済みです。既存開発ブックの値は変更していません。

この結果を受けて、公開URLは自動判定せず、利用者が公開画面のURLをsettingsの「ウェブアプリURL」へ貼り付ける明示入力方式へ設計変更しました。2026-09-17に専用ブックへpushし、Playwrightで再受入しました：初期設定2回で「バージョン」行が先頭に1.0.0、「ウェブアプリURL」行が空欄で1回だけ追加され既存値（合言葉・保持行数=2など）は全て保持。URL未入力と不正形式（別ドメインの/exec形式）の両方で案内ダイアログが出て送信0件。テスト送信は自分宛に1件届き、logへmailed=yes・fromの先頭ゼロを保持して記録（保持上限2件で最古行が削除されるローテーションも実測）。追加のCloud設定や新しいスコープは不要で、既存4スコープの承認で実行できました。受入保留は解除し、塊5以降へ進めます。

## ログ保持の合意事項

2026-09-16、うぶさん承認。塊3の実装を公開版v16へ反映しました。連続再送、未認証ログ抑止、専用コピーでの保持上限による削除を実機確認済みです。

- `log` は長期保管庫ではなく、転送結果を切り分けるための直近の履歴です。
- ログ保持上限を導入する初回更新前に、既存の `log` シートをバックアップします。バックアップの作成・読み戻し確認に失敗した場合は、新版を公開しません。
- 初回のバックアップは自動削除しません。保管先と取得日時を更新時の証跡に残します。
- 導入後は、設定した保持上限を超えた古いデータ行を自動削除します。ヘッダー行は保持件数に含めず、削除しません。
- ログの通常ローテーションでは、削除のたびにバックアップを作りません。この点だけ、共通の「破壊的操作の前に毎回バックアップする」ルールの例外とします。
- 保持上限を小さくすると、次のログ記録時に既存の古い行も削除対象になります。必要な履歴は設定変更前に別途保存してください。
- この例外は `log` の保持上限による削除に限ります。`settings`、`filter`、メールや、ログの別用途の上書き・削除には適用しません。

保持件数は `settings` の「ログの保持行数」で変更します。既定はデータ1,000行。空欄、不正値、0以下、小数は既定へ戻ります。

開発版の初回バックアップは、同じスプレッドシート内の `backup_log_b3_20260916_090649_UTC` です。2026-09-16 09:06:49 UTC（16:06:49 +07:00）に取得し、ヘッダーと既存17データ行の一致を確認しました。

専用コピー `sms-forwarder_塊2検証済_20260916` では保持上限を2件にし、Playwrightから `testSend` を3回実行しました。2026-09-16 09:40:56 UTC（16:40:56 +07:00）にヘッダーと最新2件、送信元 `0000` の文字列保持、最初のテスト行の削除を確認しました。開発版の設定・ログは前後で不変です。コピーは上限2件の検証用として残し、承認画面は既存承認のため今回は出ませんでした。

## 再送と失敗の切り分け

同じ端末・SIM・送信元・本文・受信時刻の再送は、送信済みの短期キャッシュが残っている場合に抑止します。保持期間の指定は10分ですが、サービスの都合で早期に消えることがあり、恒久的な二重送信防止は保証しません。受信時刻がない旧端末では、同じ内容の別のSMSを短期間に受けると重複扱いになる場合があります。

重複の応答は正常終了で、`mailed=false`、理由は `duplicate` です。認証されていない要求は既定で `log` に記録しません。切り分け用の「未認証も記録する」を有効にしても、SMS本文や電話番号、合言葉は残しません。

同時着信はスクリプト内のロック取得を最大30秒待って直列化します。待機上限に達した要求は、メールもログも更新しません。GAS実行履歴を確認し、失敗した要求は端末の送信履歴から手動再送してください。HTTP成功の応答に失敗JSONが含まれていても、SmsForwarderが自動再送するとは限りません。

メール送信後のラベル、キャッシュ記録、ログ記録の失敗は警告として扱い、送信済みの結果を失敗へ戻しません。警告はGASの実行履歴を確認してください。キャッシュ記録失敗後の再送や、Gmailの通信障害で送信成否が不明になった場合、実行の強制終了では二重送信を防げないことがあります。

## 復旧時の注意

コードを旧バージョンへ戻しても、削除したログは戻りません。初回更新以前のログは、保存したバックアップから復旧できます。初回更新後に追加され、その後ローテーションで削除された行は、別途保存していなければ復旧できません。

復旧は受信処理を止めてから、現在のログを退避し、バックアップのヘッダーと値を元の `log` へ戻して読み直します。受信停止・再開は、利用者の確認を得て行います。
